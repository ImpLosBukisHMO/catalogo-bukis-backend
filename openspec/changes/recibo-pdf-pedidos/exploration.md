## Current State

The backend already serves protected file downloads via `build_comprobante_response()` in
`catalogo_backend/api/utils/comprobantes.py`. That utility wraps Django's `FileResponse` with
`Content-Disposition: inline`. There is **no existing PDF generation infrastructure** — no
`xhtml2pdf`, no Django template dirs configured for custom HTML, no template files under
`catalogo_backend/`.

The order model (`PedidosModel`) has all the data needed for a receipt:
- `folio` (computed property: `f"{self.id:06d}"`)
- `cliente` FK → `UsuariosModel` (nombre, apellido, correo, telefono)
- `direccion` FK → `DireccionesModel` (calle, colonia, cp, ciudad, estado, pais)
- `estado` (TextChoices: PENDING, APPROVED, DENIED, READY, SHIPPED, COMPLETED, CANCELED)
- `subtotal_snapshot`, `precio_total`, `created_at`
- `items` (reverse FK to `PedidoProductosModel`) — all snapshot fields present

State machine (from model):
```
PENDING → APPROVED | DENIED
APPROVED → READY | CANCELED
READY → SHIPPED | CANCELED
SHIPPED → COMPLETED | CANCELED
DENIED → [] (terminal)
COMPLETED → [] (terminal)
CANCELED → [PENDING]  (reopenable)
```

Receipt is allowed from **APPROVED onward**: APPROVED, READY, SHIPPED, COMPLETED.
CANCELED with `requiere_reembolso=True` is a special case — see Open Questions.

The frontend already has a proven `comprobante.ts` service that fetches protected binary
endpoints as blobs and saves them via `URL.createObjectURL` + `<a download>`.

## Key Confirmed Facts

### 1. xhtml2pdf is NOT installed
`requirements.txt` (17 lines, read in full) has: Django, DRF, SimpleJWT, Pillow, psycopg,
gunicorn, whitenoise, dj-database-url. No PDF library present.

### 2. Dependency pinning location
`catalogo-bukis-backend/requirements.txt` — single flat file, no pyproject.toml.
Railway uses Nixpacks builder which reads `requirements.txt` directly.

### 3. No Django template infrastructure exists
`settings.py` line 59: `"DIRS": []`. `APP_DIRS: True` means Django will look for
`<app>/templates/` automatically. Templates dir must be created under
`catalogo_backend/api/templates/` (auto-discovered) OR `settings.TEMPLATES[0]["DIRS"]`
must be updated to include a project-level `templates/` folder.
**Recommended**: use `catalogo_backend/api/templates/recibo/recibo_pedido.html` — no settings
change needed thanks to `APP_DIRS: True`.

### 4. Permissions pattern is fully understood
- **Client endpoint** (`MiPedidoComprobanteUpdateView`): `[IsAuthenticated]` + queryset filtered
  by `cliente=request.user` + explicit `is_staff` check returning 403 (prevents workers from
  accessing the client route). Mirror this exactly.
- **Worker endpoint** (`WorkerPedidoComprobanteDownloadView`): `[IsAuthenticated, IsWorker]`.
  `IsWorker` checks `worker_role in ('total', 'parcial')` — role-based, NOT group-based.

### 5. Worker permission is role-based
`api/permissions.py` lines 28–40: `IsWorker` checks `user.worker_role in ("total", "parcial")`.
`worker_role` is a `CharField` on `UsuariosModel` (not a Django Group). All `is_staff=True`
users were back-filled to `worker_role='total'` via migration 0038.

### 6. State list is confirmed
`PedidosModel.EstadoPedido`: PENDING, APPROVED, DENIED, READY, SHIPPED, COMPLETED, CANCELED.
Receipt allowed for: APPROVED, READY, SHIPPED, COMPLETED.
DENIED → no receipt (never had a valid order).
CANCELED → see Open Questions.

### 7. folio property confirmed
`models.py` line 589: `return f"{self.id:06d}"` — zero-padded 6-digit integer.

### 8. Response pattern to mirror
`build_comprobante_response()` returns `FileResponse(field.open("rb"), content_type=...,
Content-Disposition: inline; filename="...")`. For the PDF, we'll generate bytes in memory
(`io.BytesIO`) rather than reading from a FileField. Use `HttpResponse` with
`content_type="application/pdf"` and `Content-Disposition: attachment; filename="recibo-{folio}.pdf"`.
(Using `attachment` vs `inline` forces browser download rather than preview — more appropriate
for a handoff receipt.)

### 9. URL naming convention
Client routes: `name="mi-pedido-{resource}"` (e.g. `mi-pedido-comprobante`).
Worker routes: `name="worker-pedido-{resource}"` (e.g. `worker-pedido-comprobante`).
New routes should follow: `name="mi-pedido-recibo"` and `name="worker-pedido-recibo"`.

### 10. No shared services.py for business logic
Views call models and utils directly. No service layer to route through.

### 11. Frontend download utility already exists
`services/comprobante.ts` — `fetchProtectedComprobante` fetches a protected binary endpoint
as a blob and extracts filename from `Content-Disposition`. `openProtectedComprobante` then
saves it. The allowlist (`PROTECTED_COMPROBANTE_PATHS`) currently allows only `/comprobante/`
paths. The new `/recibo/` paths must be added to the allowlist OR a parallel `recibo.ts`
service is created.

### 12. Worker has a per-order detail PANEL (not a separate page)
`WorkerOrdersPage.tsx` is a split-panel SPA: left = order list, right = order detail inline.
There is NO separate worker order detail *page*. The download button goes in the right panel
of `WorkerOrdersPage.tsx` — specifically inside the detail section that renders when
`selected !== null`.

### 13. Test runner confirmed (frontend)
`package.json` has `"test": "vitest run"` and `vitest@^3.2.6` in devDependencies.
**The openspec/config.yaml is STALE** — it says `runner: none` but Vitest IS installed and
running `.test.tsx` files exist (11 files found). Backend uses `python manage.py test`
(Django TestCase). No pytest/conftest.py found.

### 14. Railway deployment confirmed
`railway.toml`: Nixpacks builder, `gunicorn` start command, `migrate + collectstatic` release.
xhtml2pdf is pure-Python and Nixpacks will install it from `requirements.txt` without system-
level package installation. ✅ No friction expected.

### 15. Static assets for PDF template
`STATICFILES_DIRS = [BASE_DIR / "static"]`. If the PDF template needs CSS/images (e.g. logo),
they can reference inline styles or base64-encoded assets. External URLs may fail in Railway
depending on network policies — **inline styles are safest** for the PDF template.

## Open Questions

### Q1: CANCELED orders with `requiere_reembolso=True`
The client paid before cancellation. Should the receipt be downloadable for CANCELED orders?
Arguments for yes: the client has a payment record and may need proof.
Arguments for no: the order was canceled — the receipt would be misleading.
**Recommend asking the user before spec.** Current plan: exclude CANCELED.

### Q2: Content-Disposition — `attachment` vs `inline`
`attachment` forces browser download; `inline` opens in browser PDF viewer.
For the client (handoff receipt), `attachment` seems right. For the worker, same.
But the existing `comprobante` pattern uses `inline`. Confirm preference.

### Q3: Receipt filename convention
Proposal: `recibo-{folio}.pdf` (e.g. `recibo-000042.pdf`).
Confirm or adjust.

### Q4: Branding / logo on the receipt
Does the PDF need the store logo? If yes, where does the asset live (filesystem path or URL)?
This affects template complexity.

### Q5: openspec/config.yaml frontend testing stale entry
Config says `runner: none` for frontend but Vitest 3.2.6 is installed and `.test.tsx` files
exist. Should the config be updated as part of this change, or separately?

## Risks / Gotchas

1. **xhtml2pdf transitive deps** — installs html5lib, Pillow (already present), reportlab,
   svglib. All pure-Python. Railway Nixpacks should handle without issues.

2. **Django template rendering in a view returning PDF** — must call `render_to_string()`
   and pass the resulting HTML to `pisa.CreatePDF()`. Template must be discovered correctly
   (APP_DIRS path).

3. **`direccion` can be NULL** — `PedidosModel.direccion` is `SET_NULL`. The template and
   view must handle the case where the address is absent (older orders or manual orders).

4. **Snapshot field completeness** — `PedidoProductosModel` has both snapshot fields
   (`producto_nombre_snapshot`, `precio_unitario_snapshot`, etc.) and legacy nullable fields.
   The template should use snapshot fields exclusively; legacy fields may be empty.

5. **`content_type` leak** — The client receipt endpoint must still guard against
   `is_staff=True` users (workers) accessing the client route, exactly as `MiPedidoComprobanteUpdateView` does.

6. **Frontend allowlist in `comprobante.ts`** — If the `/recibo/` paths are not added to
   `PROTECTED_COMPROBANTE_PATHS`, calling `fetchProtectedComprobante` for a receipt URL will
   throw `"Comprobante URL must target a protected comprobante endpoint"`. Either update the
   allowlist or create a parallel service — naming becomes a concern (comprobante.ts handles
   both comprobante AND recibo paths if extended).

7. **Worker detail is inline, not a page** — The download button must fit within the existing
   right-panel layout of `WorkerOrdersPage.tsx` without creating a new page or route.

8. **400-line budget** — Estimated touched lines:
   - Backend: ~100 (new view ×2, util helper, template, urls, requirements, test file ~50 lines)
   - Frontend: ~60 (service update, button in 2 pages, allowlist update, test)
   - Total estimate: ~160–200 lines. **Budget risk: Low.** Single PR is viable.

Proceed directly to `sdd-propose-claudio`. All architectural questions are resolved except

`build_comprobante_response()` but generates bytes on the fly instead of reading a FileField.
